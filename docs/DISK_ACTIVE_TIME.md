# 디스크 활성 시간 설계

작성: 2026-11-05 · 브랜치: `main` (`7f4ff5e` 다음)

상태: **측정 쪽 설계 끝(붙이기 1) · 앱 설계 끝(4장) · 보조 프로그램 끝(붙이기 2, 2026-11-06).** 붙이기 3·4(5장)는 앱 대화가 이 문서에 이어서 적는다.

디스크 카드의 바쁜 정도에 Windows 작업 관리자의 '활성 시간'을 더한다. 디스크 I/O 설계(`DISK_IO.md`)는 바쁜 정도를 평균 동시 요청(A안)으로 정하고 '써 보면서 뺄지 보강할지 정한다'고 두었는데, 이 문서가 그 보강이다. 재는 방법은 `Diagnostics/DiskActiveProbe`(1~4단계, 결과는 그 README)에서 확인했다. 여기에는 그 결과로 정한 것, 보조 프로그램과 앱 사이의 약속, 지킬 규칙, 앱 설계에서 정할 것을 적는다. `DISK_IO.md`의 원칙(지어낸 값 금지, 값마다 상태와 측정 시각, 중복 합산 금지)을 그대로 따른다.

## 1. 정한 것

### 뜻 (2026-11-04~05 사용자 결정)

- **활성 시간** = 그 디스크에 요청이 하나라도 걸려 있던 시간의 비율. Windows 작업 관리자의 '활성 시간'이나 Linux `io_ticks`와 같은 뜻이다. 평균 동시 요청과는 다르다: 무작위 4 KiB 동시 8 부하에서 활성 100%, 평균 동시 요청 7.08
- **물리 디스크별.** 볼륨·파티션별로 세어 더하지 않고 이벤트를 먼저 물리 디스크로 모은다(같은 디스크의 볼륨에 겹친 요청을 두 번 세면 100%를 넘는다). 디스크 이미지는 뺀다. 디스크는 IOBlockStorageDriver의 IORegistry 항목 ID로 구분한다 = 앱의 `DiskDevice.id`·`Metric.disk*(id)`와 같은 값
- **내장 SSD = 디스크 I/O ∪ 캐시 비우기 ∪ TRIM.** 다른 디스크(SD 카드·외장)는 디스크 I/O만 센다(SSD 드라이버 이벤트가 없음). 캐시 비우기·TRIM 이벤트가 안 보이는 macOS면 디스크 I/O만으로 재고, 그렇다고 표시한다
- **출처는 커널 추적(kdebug)**이라 보조 프로그램(root)이 잰다. 권한 없이 읽는 값(IOBlockStorageDriver 통계·IOReport·SMART)으로는 활성 시간을 만들 수 없다(DiskActiveProbe README '왜 이 방법인가')
- **추적을 못 쓸 때는 '추정'**: 보조 프로그램이 없을 때, 다른 추적 도구가 쓰는 중일 때, 설정에서 껐을 때. 드라이버 통계로 낸 그 구간의 평균 동시 요청을 100%에서 자른 값이다

### 추적 (DiskActiveProbe 3·4단계 결정)

- 읽는 방식 **w**: `KERN_KDBUFWAIT`로 커널 안에서 기다리다가 버퍼의 절반이 차면 바로, 아니면 1초 경계 30 ms 뒤에 읽는다
- **늘 켜 두되 비켜주기**: 추적 도구의 실행 이벤트를 보면 바로 놓고, 그 도구가 끝나고 10초 뒤에 다시 잡는다. Instruments가 켜져 있는 동안은 계속 비켜준다(그동안 추정)
- 잠자기에 따로 할 일은 없다(쥔 채로 깨어나 이어서 잰다). 깬 뒤 커널 기록이 켜져 있는지만 본다

### 붙이기 (2026-11-05 사용자 결정)

- 켜는 방식: **설정 스위치, 기본 켬.** 끄면 바로 추적을 놓고 추정으로 보인다
- 범위: 패널의 디스크 카드·펼친 상세·설정. **위젯은 이번에 뺀다**(디스크 위젯을 정할 때 함께)
- **앱 설계에서 정한다**: 추적을 쥐는 때, 추적 값을 믿을 수 없을 때의 표시, 화면과 시안 → 4장
- 설계 문서는 이 파일 하나다. 앱 대화가 이어서 고쳐 쓴다

## 2. 확인된 사실 (DiskActiveProbe, MacBookPro18,1 · macOS 27.2)

| 항목 | 결과 | 단계 |
|---|---|---|
| 정확도 | 작업 수·바이트가 드라이버 통계와 같음(내장 SSD·SD 카드 모두 100.0%). 짝 못 맞춤·늦게 온 이벤트 0 | 1·2 |
| 추정과의 차이 | 실사용 10분: 1초마다 평균 절대 2.3%p, 20%p 넘게 다른 1초 17번, 최대 90%p. 밤새 5시간: 평균 0.30%p, 20%p 넘게 다른 1초 57번. 짧게 몰릴 때 크게 틀린다(추적 7~13%에 추정 100%). 오래 걸리는 요청(쉬던 SD 카드가 깨어나는 약 3초)은 추적으로는 그동안 100%, 추정으로는 끝난 1초에만 100% | 2·4 |
| 캐시 비우기·TRIM의 몫 | 실사용 +0.1%p. F_FULLFSYNC가 몰리면 10% → 약 94%. 밤새 바쁜 시간에 캐시 비우기 +2.1%, TRIM +0.4% | 2·4 |
| 비용 (도구) | 가만히 한 코어의 0.19%(1초에 1.93 ms), 무거운 부하(초당 약 17만 작업)에서 약 6%. 메모리 3.5 MB(무거운 부하 최대 18.4 MB)와 커널 버퍼 22.5 MiB(고정 메모리) | 4 |

| 오래 켜 두기·잠자기 | 5시간 동안 잃음 0, CPU 일정. 잠자기 6번 모두 쥔 채로 깨어나 이어서 잼. mach_absolute_time이 잠든 동안 멈춰서 누적값도 깨어 있던 시간만 | 4 |

## 3. 구조

```
[앱] CollectionScheduler ── 요청 (XPC, 1초 또는 10초마다) ──▶ [보조 프로그램] HelperService
[앱] 활성 시간 계산 (새로) ◀── 마지막 1초 경계의 누적값 ── [보조 프로그램] 추적 서비스 (새로): 엔진 + hold 규칙, 추적 스레드 하나
[앱] DiskCollector (지금 그대로): 드라이버 통계 → 추정·대조
```

- 보조 프로그램은 %를 내지 않는다. 디스크별 **누적 활성 시간(ns)**과 그 기준 시각(1초 경계)만 갖고 있다가 요청에 바로 답한다
- 앱은 받을 때마다 앞에 받은 것과의 차이로 %를 낸다. 패널 1초·닫힘 10초 어느 간격이든, 간격이 바뀌어도 같은 누적값에서 나온다
- 추정과 대조는 앱이 이미 읽는 드라이버 통계(`DiskCollector`)로 한다. 보조 프로그램은 드라이버 통계를 읽지 않는다

### 3.1 넘기는 값

Shared에 둘 Codable 값 타입 (이름과 모양은 예):

```swift
/// 보조 프로그램이 주는 디스크 활성 시간 누적값 (docs/DISK_ACTIVE_TIME.md 3.1)
nonisolated struct DiskActivitySample: Codable, Hashable, Sendable {
    enum State: String, Codable, Hashable, Sendable {
        case tracing    // 추적 중. boundary·disks는 이 회차의 마지막 1초 경계 값
        case starting   // 잡았지만 아직 1초 경계가 없음
        case otherTool  // 다른 추적 도구가 쓰는 중 (비켜줌 또는 그 도구가 먼저 쥐고 있음)
        case off        // 쥐고 있지 않음
        case failed     // 잡기·읽기 실패 (까닭은 답의 두 번째 값)
    }
    var state: State
    /// 다른 추적 도구 이름 (알면, 예: "xctrace")
    var otherTool: String?
    /// 회차: 추적을 잡은 시각 (ns, mach_absolute_time). 보조 프로그램이 다시 떠도 겹치지 않는다.
    /// 누적값은 같은 회차 안에서만 이어진다
    var generation: UInt64
    /// 누적값의 기준 시각 (ns, mach_absolute_time = 앱의 CLOCK_UPTIME_RAW. 잠든 시간은 빠짐)
    var boundary: UInt64
    /// 그 회차의 디스크 목록에 있는 물리 디스크 모두 (요청이 없었으면 0)
    var disks: [Disk]
    /// 이 회차에서 커널 버퍼가 넘친 횟수 (TRACE_LOST_EVENTS)
    var lostEvents: UInt64
    /// 내장 SSD의 캐시 비우기·TRIM 이벤트를 받는지 (거짓이면 디스크 I/O만)
    var flushTrim: Bool

    struct Disk: Codable, Hashable, Sendable {
        /// IOBlockStorageDriver IORegistry 항목 ID (앱의 DiskDevice.id)
        var id: UInt64
        /// 활성 누적 (ns). 내장 SSD는 디스크 I/O ∪ 캐시 비우기 ∪ TRIM
        var activeNs: UInt64
        /// 끝까지 본 디스크 I/O 작업 수와 바이트 (드라이버 통계의 읽기+쓰기와 대조)
        var operations: UInt64
        var bytes: UInt64
    }
}
```

- 요청은 전력과 따로 둔다(한쪽이 실패해도 다른 쪽은 그대로). 답은 지금처럼 (JSON, 문제 글)이고, 디스크 2개면 수백 바이트다
- 요청 이름·인자(간격을 넘길지, 끄라는 요청을 따로 둘지)는 쥐는 때(4.1)와 함께 앱 설계에서 정한다
- 새 요청도 `latestPower`처럼 실행 파일이 바뀌었는지 먼저 본다. 앱을 다시 빌드한 직후 옛 보조 프로그램이 새 요청을 모르는 동안은 실패로 오는데, 실행 파일 교체 규칙(`HelperLifecycle.exitSoon`)으로 곧 새 파일로 다시 뜨므로 그동안은 추정

### 3.2 앱의 계산 (제안. 앱 설계에서 확정)

- 활성 % = (activeNs₂ − activeNs₁) ÷ (boundary₂ − boundary₁) × 100. 같은 회차(generation)일 때만 센다. 0~100%로 자른다(1초 경계 시각의 반올림 몫)
- 같은 boundary를 다시 받으면 새 값이 아니다. 앞 값을 그대로 두고 그래프 기록에 더하지 않는다(전력의 같은 표본 규칙과 같음)
- 측정 시각 = boundary. 앱 시각으로는 `지금 − (CLOCK_UPTIME_RAW 지금 − boundary)`. 받을 때 boundary는 약 0~1초 지난 값이다
- 추적 값이 없는 구간은 추정으로, 드라이버 통계 값도 없으면(잠든 구간 등) 준비 중으로: 첫 답, 회차가 바뀐 구간, 잠든 구간(앱의 `DiskMeter`처럼), boundary나 누적값이 줄어든 경우. lostEvents가 늘어난 구간은 4.2
- 새로 보인 디스크는 기준점만 잡고, 빠진 디스크는 지운다(`DISK_IO.md`와 같음)
- 추정 = min(평균 동시 요청, 1) × 100. 같은 구간의 드라이버 통계로 낸다(앱이 이미 셈). 닫힘 10초 구간이면 10초 평균을 자르므로 몰림에서 더 크게 틀린다
- 오래됨: 전력과 같은 기준(요청 간격 × 2.5 + 2초)을 boundary에 쓴다

### 3.3 추적 서비스 규칙 (DiskActiveProbe hold에서 옮김. 바꾸면 그 도구로 다시 시험한다)

1. **잡기**(`acquireTrace`): 잡기 직전에 프로세스 목록을 한 번(1.9~2.5 ms) 보고, 추적 도구가 돌고 있으면 기다린다(처음 잡을 때도: 먼저 켜 둔 Instruments). 살아 있는 전경 소유자(다른 도구)가 있으면 손대지 않고 otherTool로 두고 2초마다 다시 잡아 본다. 소유자 없이 남은 추적은 끄고 해제한 뒤 잡는다. 배경 소유자(tailspind)에게서는 가져온다
2. **설정**: 버퍼는 작게 요청한다(커널이 최솟값으로 올림: 이 Mac은 368,640개 = 22.5 MiB, CPU·보조 프로세서 수에 따라 다름). 형식 필터는 디스크 I/O(`DBG_FSYSTEM/DBG_DKRW`)·디스크 명령(`DBG_FSYSTEM/DBG_IOCTL`)·SSD 드라이버(`DBG_DRIVERS/DBG_SSD`, 캐시 비우기·TRIM). 남은 사용자 플래그(멈춤·연속 시각·특정 이벤트에서 멈춤)를 끈다. 시각은 mach_absolute_time
   - 형식 필터는 종류 단위라서, SSD 드라이버 이벤트 중 명령마다 찍히는 것(무거운 부하에서 이벤트의 약 60%)도 커널에서 읽은 뒤에 버린다. 무거운 부하 CPU의 70%가 읽기인 까닭이다
3. **읽기**: w, 한 번에 65,536개(4 MiB). 읽은 때 − 20 ms까지 처리하고, 1초 경계마다 디스크별 누적값을 만들어 마지막 것만 둔다
4. **1초마다**: 소유자가 나인지 본다(`ktrace.owning_pid`). 아니거나 읽기가 EBUSY면 밀려난 것이다 → 남의 설정은 건드리지 않고(내가 아직 소유자면 내 설정만 해제) otherTool로 두고 2초마다 다시 잡아 본다
5. **비켜주기**: 추적 중에 실행 이벤트(`TRACE_STRING_EXEC`)의 이름이 추적 도구(`fs_usage`·`sc_usage`·`latency`·`ktrace`·`xctrace`·`Instruments`·`sysdiagnose`)면 바로 기록을 끄고 해제한다 → otherTool(이름). 그동안 그 pid만 보고(`kill(pid, 0)`), 끝나고 10초 뒤 1번대로 다시 잡는다. spindump는 늘 떠 있는 데몬이라 넣지 않는다
6. **디스크 목록**: 30초마다 구성 표식(IOBlockStorageDriver·IOMedia 항목 ID)만 보고, 바뀌었을 때만 다시 만든다. 모르는 장치가 보이면 2초 뒤에. 디스크가 아닌 장치(`/dev/null` 등)는 뺀다
7. **잠자기**: 깬 뒤(벽시계 − mach 시각 > 5초) 커널 기록이 꺼져 있으면 내려놓고 다시 잡는다. 시험에서는 한 번도 없었다
8. **놓기**: 기록을 끄고 해제한다. 해제하면 커널이 tailspind를 배경으로 되돌린다
   - 앱 연결이 모두 끊기면 바로(팬의 `appDisconnected`처럼. 쥐는 때를 어떻게 정하든)
   - 설정을 끄면 바로
   - 보조 프로그램이 끝날 때: SIGTERM, 연결이 모두 끊기고 5초, 실행 파일 교체
   - 충돌 신호(SIGTRAP·SIGSEGV·SIGBUS·SIGILL·SIGABRT·SIGFPE): 힙을 쓰지 않는 `emergencyRelease`
   - kill -9만은 처리기가 돌지 않아 남는다 → 9번
9. **시작할 때 정리**: 보조 프로그램이 뜰 때 소유자 없이 남은 추적이 보이면 끄고 해제한다(팬의 `cleanUpLeftovers`와 같은 자리). 설정이 꺼져 있어도 한다
10. **끝낼 때**: 지금 SIGTERM 처리(`main.swift`)는 받자마자 `exit(0)`하므로, 그 전에 부른 스레드에서 기록을 끄고 해제해야 한다. 추적 스레드는 `KERN_KDBUFWAIT` 안에서 최대 약 1초 기다리는데, 기다리는 동안 커널은 ktrace 잠금을 풀어 두므로 다른 스레드의 해제가 막히지 않는다. 추적 스레드의 읽기·처리와 겹치지 않게 잠금을 둔다. 기다리는 중에 다른 스레드에서 해제해도 되는지는 붙이기 2에서 확인한다(시험: 기다리는 중에 SIGTERM → `sudo ./run.sh status`)
    - 확인함(2026-11-06, 5.1 결과): 추적 스레드가 커널 안에서 기다리는 중에 SIGTERM을 받은 스레드가 놓았고, 커널 기록에 바로 'promoting background tool'이 남았다

### 3.4 비용 목표

- 보조 프로그램의 추적 서비스: 가만히 1초에 약 1 ms(한 코어의 약 0.1%). 도구의 1.93 ms에서 이 도구만 하던 드라이버 통계(0.44 ms)·1초 표본 쓰기(0.46 ms)를 뺀 어림이다. 무거운 부하에서 한 코어의 약 6%
- 메모리: 보조 프로그램에 더해지는 양은 도구 전체(가만히 3.5 MB, 무거운 부하 최대 18.4 MB, 읽기 버퍼 4 MiB 포함)보다 작거나 비슷하다. 그 밖에 커널 고정 메모리 22.5 MiB
- 다른 프로그램: 시스템 콜 한 번 +11 ns
- 앱: 요청 하나(1초 또는 10초마다), 작은 JSON, 디스크마다 뺄셈 몇 번

## 4. 앱 설계에서 정할 것 (2026-11-05 사용자 결정으로 넘김)

자료와 선택지를 적는다. '제안'은 이 도구 쪽 대화의 생각이고, 정하는 것은 앱 설계다.

### 4.1 추적을 쥐는 때

- 자료
  - 전력(powermetrics)은 앱이 묻는 동안만 돈다. 묻지 않은 지 max(요청 간격 × 3, 15초)가 지나면 멈춘다. 앱은 화면이 꺼지면 묻지 않는다
  - 다시 잡을 때 드는 것: 커널 버퍼 22.5 MiB를 새로 받고 디스크 목록을 만든다(수 ms). 다시 잡은 첫 구간은 추적 값이 없다(3.2). tailspin이 켜진 Mac이면 잡을 때마다 tailspin 최근 기록이 지워진다
  - 쥐고 있는 동안의 비용은 2장(다른 프로그램은 시스템 콜 한 번 +11 ns)
- 선택지: ① 앱이 묻는 동안만(전력과 같은 규칙, 제안) ② 앱이 연결된 동안 늘(화면이 꺼져도) ③ 패널이 열린 동안만(닫힌 동안의 그래프 기록은 추정)
- 같이 정할 것: 요청 이름·인자, 설정을 끄면 바로 놓게 하는 요청, 화면이 꺼진 동안의 수집(지금 30초마다)에서도 물을지
- **정함 (2026-11-06 사용자 결정)**
  - 앱이 묻는 동안만 쥔다. 묻지 않은 지 max(요청 간격 × 3, 15초)가 지나면 놓는다(전력과 같은 규칙). 패널이 닫혀 있어도(10초마다 물음) 쥔다
  - 화면이 꺼진 동안은 묻지 않는다. 약 30초 뒤 추적을 놓고 그동안 기록은 추정, 화면이 켜지면 다시 잡는다
  - 놓기 요청 `releaseDiskActivity()`를 따로 둔다. 설정을 끄는 순간 앱이 보내고 보조 프로그램은 바로 놓는다
  - 요청 `latestDiskActivity(intervalMilliseconds:reply:)`. 간격은 전력처럼 1,000·10,000만 받고 놓는 때를 재는 데만 쓴다. 답은 (DiskActivitySample JSON, 문제 글). 전력 요청과 따로 두고 실행 파일 교체를 먼저 본다

### 4.2 추적 값을 믿을 수 없을 때

- 자료
  - 대조: 앱이 받은 작업 수·바이트(3.1)를 드라이버 통계의 읽기+쓰기와 견준다. 1·2단계에서 100.0% 같았다
  - 누적값의 기준 시각(1초 경계)과 앱이 드라이버 통계를 읽는 시각이 달라서 짧은 구간끼리는 어긋난다. 무거운 부하(초당 17만 작업)에서는 1초만 어긋나도 17만 개 차이다 → 긴 창(예: 5분, 작업 1,000개 이상)에서 비율로 본다(예: 5% 넘게 어긋나면)
  - 잃음(lostEvents가 늘어남)이 있던 구간은 그 구간 값이 모자란다
  - 지금까지 실험에서 둘 다 없었다. macOS가 바뀌어 이벤트가 사라지거나, 추적에 안 보이는 I/O(APFS가 IOKit으로 바로 보내는 I/O 등)가 생기는 경우를 잡으려는 것이다
- 선택지: ① 추정으로 바꾸고 상세에 까닭(제안) ② 측정 불가(DiskActiveProbe 1단계 때 적어 둔 규칙)
- **정함 (2026-11-06 사용자 결정)**
  - 대조가 어긋난 디스크는 추정으로 바꾼다(까닭 '대조 어긋남'). 그 디스크만
  - 기준: 디스크마다 5분 창, 그 창의 드라이버 통계 작업 수(읽기+쓰기)가 1,000개 이상일 때만 견준다. 보조 프로그램의 작업 수와의 차이가 5% + 창 끝 몫보다 크면 어긋남
    - 창 끝 몫 = 창의 시작과 끝에서 앱이 드라이버 통계를 읽은 그 한 구간의 작업 수. 보조 프로그램 값은 마지막 1초 경계 값이라 앱이 읽은 때보다 0~1초 앞서서, 창 양 끝이 최대 1초 어긋난다
    - 근거(2단계 실사용 10분 기록, 창을 1초 밀어 봄): 5%만이면 창 298개 중 4개(1.3%, 최대 8.8%)가 잘못 어긋남 → 끝 몫을 더하면 0개. 실제로 10%를 잃으면 창의 94%에서 잡힌다
    - 창은 같은 회차 안에서만 이어 간다(회차가 바뀌거나 잠들면 새로 시작)
  - 다음 5분 창이 다시 맞으면 추적 값으로 돌아간다
  - 잃음(lostEvents가 늘어남)이 있던 구간은 그 구간만 추정. 다음 구간부터 추적 값(엔진은 잃는 순간 걸려 있던 요청을 정리한다)

### 4.3 화면 (시안 캔버스 'MonitorTool 화면 시안' · '디스크 활성 시간' 줄)

- 디스크 카드: 지금 열은 이름·읽기·쓰기·동시(평균 동시 요청). 활성 %를 넣을 자리(동시 열을 바꾸기, 열 더하기, 다른 모양)
- 평균 동시 요청: `DISK_IO.md`의 A안('써 보면서 뺄지 보강할지 정한다'). 카드에 둘지, 상세로 옮길지, 뺄지
- 펼친 상세: 활성 시간 그래프(축을 0~100%로 고정할지), 값 표
- '추정' 표시: 카드 값, 상세, 그래프 선(추적과 추정이 섞인 구간)
- 상태 문구: 추적 · 추정(까닭: 보조 프로그램 없음 · 다른 추적 도구 사용 중 · 꺼 둠 · 대조 어긋남) · 준비 중 · 오래됨 (· 측정 불가). 설명 문단 없이 문구 규칙대로
- 설정: 스위치 자리(보조 프로그램 탭 등)와 문구, 다른 도구에 비켜준 상태를 보일지
- 그래프 기록: 디스크마다 계열 하나 더(예: `Metric.diskActive(id)`). 30분 기록·30초 묶음 저장 원칙은 그대로
- **정함 (2026-11-06 사용자 결정)**
  - 디스크 카드: 열은 읽기 · 쓰기 · 활성. 활성 칸은 숫자(%) 뒤에 짧은 막대(약 44pt, 0~100%). 평균 동시 요청은 카드에서 뺀다
  - 추정이면 그 디스크 줄만 숫자 앞에 ≈, 막대는 두 번째 계열 색(50%). 디스크마다 따로 본다(대조 어긋남은 디스크마다)
  - 펼친 상세: 그래프 기간 → 디스크 고르기 → 기기 이름 → **활성 시간 그래프**(새로, 축 0~100% 고정, 눈금 100 · 50 · 0%) → 속도 → 평균 동시 요청(그래프 그대로) → 값 표 → SMART
  - 활성 시간 그래프 제목 옆에 지금 값(추정이면 ≈). 그 아래 세부 줄은 추정이면 '추정'(까닭은 적지 않음), 내장 SSD를 디스크 I/O만으로 잴 때(`flushTrim` 거짓) '디스크 I/O만', 추적 중이면 비움
  - 그래프의 추정 구간은 연한 색 선(두 번째 계열 색)으로, 추적 구간과 이어서 그린다
  - 준비 중·오래됨은 지금 규칙대로: 카드 칸은 준비 중이면 '—'(막대 비움), 오래됨은 흐리게
  - 설정: '보조 프로그램' 탭, 상태 상자 아래 '측정' 묶음에 '디스크 활성 시간' 스위치(기본 켬). 상태 세부 줄은 두지 않는다. 보조 프로그램이 꺼져 있어도 켜고 끌 수 있다
  - 추정의 까닭(보조 프로그램 없음 · 다른 추적 도구 · 꺼 둠 · 대조 어긋남 · 추적 준비 중 · 잃음 · 실패)은 화면에 보이지 않는다. 보조 프로그램 기록(NSLog)과 앱의 DEBUG 출력으로 본다
  - 그래프 기록: 디스크마다 `Metric.diskActive(id)` 계열 하나 더. 표본마다 출처(추적·추정)를 함께 둬서 추정 구간을 연한 색으로 그린다. 30분 기록·30초 묶음 저장 원칙은 그대로

### 5.3 실사용 점검 (붙이기 4)

- 하루 켜 두기: 잠자기·깨기, 외장 디스크 꽂고 빼기, 몰림 뒤 메모리가 돌아오는지(가볍게 한 뒤로는 오래 켜 둔 기록으로 아직 보지 않음)
- 비용: ResourceProbe로 앱·보조 프로그램을 추적 켬·끔으로 잰다. 목표는 3.4
- 함께 쓰기: Instruments·xctrace·fs_usage를 켜고 끄며 비켜주기·다시 잡기·상태 표시
- 값 대조: 도구와 보조 프로그램은 추적을 동시에 쥘 수 없다. 앱 설정을 끄고 도구의 `sudo ./run.sh live`로 같은 부하를 재서 견주거나, 2단계에서 잰 부하별 값(무작위 4 KiB 동시 1 약 90%, 동시 8 약 100%, 순차 읽기 1 MiB 약 94%)과 견준다
- 끝내기: 앱 끄기·보조 프로그램 끄기(SIGTERM)·충돌 뒤 `sudo ./run.sh status`로 추적이 남지 않았는지. kill -9 뒤에는 남으므로 다음 시작 때 정리되는지
